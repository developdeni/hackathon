# Tanap AI — полный журнал проекта и инструкция

Последнее обновление: **17 сентября 2026 года**.

Этот файл хранит фактическое состояние Tanap AI: что уже сделано, как работает приложение, какой интерфейс реализован, что проверено, чего пока нет и как устанавливать или обновлять приложение. После каждого заметного изменения нужно обновлять разделы «Текущее состояние», «Проверки» и «История работ».

## 1. Кратко о продукте

**Tanap AI** — мобильное приложение для фермера и агронома. В полной версии оно должно объединять три направления агротехнологического хакатона:

1. GIS и спутниковую аналитику полей;
2. прогнозирование урожайности и агрориски;
3. компьютерное зрение в агрономии.

Главная продуктовая цепочка:

> Поле → сигнал о возможной проблеме → выездной осмотр → фотография → анализ → подтверждение агронома → история и дальнейшее действие.

Сейчас реализована базовая часть этой цепочки: **поле → осмотр с фотографией → локально сохранённая история**. Реального AI-анализа, спутниковых данных и прогноза урожайности пока нет.

## 3. Что в приложении настоящее, а что демонстрационное

### Настоящее и работающее на уровне кода

- Навигация между экранами.
- SQLite-база на ноутбуке.
- Создание и чтение записей осмотра через локальный HTTP API.
- Системная камера и галерея через Expo Image Picker.
- Загрузка выбранного изображения в постоянное хранилище backend на ноутбуке.
- Запрос геопозиции через системное разрешение.
- Нативная карта через Apple Maps на iOS.
- Получение полей с ноутбука на iPhone через Wi-Fi — подтверждено серверными логами.

### Демонстрационные данные

- Названия полей.
- Площадь полей.
- Выбранные культуры.
- Координаты и границы полей.
- Название «Демо-хозяйство».

Эти данные не относятся к реальному фермеру, кадастру или хозяйству. В интерфейсе они отмечены словом **ДЕМО**.

### Чего приложение не имитирует

Приложение не создаёт случайные AI-результаты, проценты уверенности, диагнозы болезней или прогнозы урожая. На соответствующих местах показывается честный текст о том, что аналитика ещё не подключена.

## 4. Пользовательский сценарий

1. Пользователь запускает локальный backend и Metro на ноутбуке.
2. iPhone и ноутбук находятся в одной Wi-Fi сети.
3. Пользователь открывает Tanap AI.
4. Получает список демонстрационных полей с ноутбука.
5. Нажимает на поле.
6. Видит культуру, приблизительную площадь и условную границу на карте.
7. Нажимает «Новый осмотр».
8. Делает фото или выбирает его из галереи.
9. Пишет заметку.
10. При желании добавляет координаты текущего положения.
11. Нажимает «Сохранить осмотр».
12. Телефон отправляет multipart-запрос в FastAPI.
13. Ноутбук сохраняет запись в SQLite и фотографию в `backend/data/uploads/`.
14. Открывается сохранённый осмотр.
15. При возвращении в поле осмотр появляется в общей серверной истории.

Минимум для сохранения — фотография или текстовая заметка. Геопозиция необязательна.

## 6. Как устроены данные

### Поле `Field`

- `id` — постоянный строковый идентификатор;
- `name` — название;
- `cropType` — культура;
- `areaHa` — площадь в гектарах;
- `boundary` — массив координат границы;
- `isDemo` — признак демонстрационных данных;
- `inspectionCount` — число осмотров.

### Осмотр `Inspection`

- `id` — уникальный строковый идентификатор;
- `fieldId` — поле, к которому относится осмотр;
- `createdAt` — время создания в UTC;
- `note` — заметка агронома;
- `photoLocalUri` — путь к локальной фотографии;
- `latitude` и `longitude` — необязательные координаты;
- `status` — сейчас всегда `saved`.

### SQLite на ноутбуке

База находится в `backend/data/tanap.db`. При первом запуске FastAPI:

1. создаёт таблицу `fields`;
2. создаёт таблицу `inspections`;
3. включает внешние ключи;
4. включает режим WAL;
5. добавляет демонстрационные поля через `INSERT OR IGNORE`.

Повторный запуск не удаляет пользовательские осмотры и не создаёт дубли полей.

### Фотографии

Фото от камеры или галереи отправляется multipart-запросом в FastAPI. Сервер сохраняет файл в `backend/data/uploads/`, а SQLite хранит путь `/uploads/<имя файла>`. Приложение получает HTTP URL и показывает изображение с ноутбука.

Данные существуют только на ноутбуке. Облачной копии и резервного копирования нет. Удаление приложения с iPhone больше не удаляет серверные осмотры, однако удаление папки `backend/data` уничтожит базу и фотографии.

## 10. Как обновлять приложение во время разработки

Есть два вида изменений.

### Изменения только TypeScript и интерфейса

Примеры:

- текст и цвета;
- расположение блоков;
- новые экраны на существующих библиотеках;
- работа SQLite;
- логика сохранения;
- демонстрационные данные.

Для таких изменений переустанавливать приложение на iPhone обычно не нужно:

1. сохранить изменённые файлы;
2. запустить `./scripts/start-local.sh` из корня проекта;
3. открыть установленный Tanap AI;
4. Expo загрузит новый JavaScript;
5. во время разработки Fast Refresh часто обновляет экран автоматически.

Если обновление не появилось, закрыть Tanap AI, открыть снова или нажать `r` в терминале Metro.

### Изменения нативной части

Нужна повторная сборка и установка, если изменились:

- нативные зависимости;
- разрешения iOS;
- `app.json` с нативными параметрами;
- bundle identifier;
- иконка или splash screen;
- Expo SDK или React Native;
- подключаемые модули камеры, карты, уведомлений и других устройств.
- настройки доступа к локальной сети или небезопасному HTTP.

После таких изменений нужно снова выполнить iOS-сборку и установить `.app` на телефон.

### Обновление версии

Перед отдельной сборкой для демонстрации изменить в `mobile/app.json`:

```json
{
  "expo": {
    "version": "1.0.1",
    "ios": {
      "buildNumber": "2"
    }
  }
}
```

Пользовательская версия (`version`) видна как версия продукта. `buildNumber` должен увеличиваться для каждой новой iOS-сборки, предназначенной для распространения.

### Важная особенность пути проекта

Путь содержит кириллицу:

```text
/Users/deni/Documents/ChatGPT/хакатон
```

В текущем React Native podspec Hermes есть ошибка обработки такого пути: CocoaPods смешивает кодировки `ASCII-8BIT` и `UTF-8`. Поэтому прямой `npx expo run:ios` из этой папки сейчас завершается ошибкой. Первая успешная iOS-сборка была выполнена из временной копии с латинским путём.

Надёжный способ повторной сборки:

```bash
BUILD_DIR=$(mktemp -d /tmp/tanap-ai-ios.XXXXXX)
rsync -a \
  --exclude node_modules \
  --exclude ios \
  --exclude .expo \
  "/Users/deni/Documents/ChatGPT/хакатон/mobile/" \
  "$BUILD_DIR/"
cd "$BUILD_DIR"
npm ci
npx expo run:ios --device 00008110-001425580A50201E
```

Команда:

1. создаёт временную папку с латинским путём;
2. копирует актуальные исходники;
3. устанавливает точные зависимости из lockfile;
4. создаёт нативный iOS-проект;
5. собирает приложение;
6. подписывает его;
7. устанавливает на подключённый iPhone;
8. запускает Metro.

## 13. Известные ограничения и риски

- Проект пока не закоммичен в git; файлы отображаются как новые. До серьёзных изменений нужно создать первый осмысленный коммит.
- Нет резервной копии пользовательских осмотров.
- Удаление `backend/data` удаляет базу и фотографии.
- При выключенном ноутбуке или остановленном backend приложение не получает поля и осмотры.
- При смене Wi-Fi адрес ноутбука может измениться; `scripts/start-local.sh` автоматически обновляет `.env.local`.
- Демонстрационные границы не являются кадастровыми.
- Нет обработки ошибок повреждённого изображения.
- Нет удаления и редактирования осмотра.
- Нет миграций версий схемы базы кроме первоначального создания таблиц.
- Development-сборка зависит от компьютера и Metro.
- Сборка из кириллического пути блокируется ошибкой Hermes/CocoaPods.
- Сертификат разработки и provisioning profile имеют ограниченный срок действия; приложение может потребовать повторной подписи и установки.
- Точность будущего AI нельзя обещать до выбора данных, модели и проверки на отдельных примерах.
